# Complex Avalonia Components Roadmap

Basic Avalonia support covers theme resources, generated tokens/icons, the demo
shell, and the first basic control subset. It does not imply parity for complex
components. The components below require dedicated contracts, performance
budgets, memory budgets, accessibility plans, platform divergence tracking, and
large-data tests before implementation.

## Shared Architecture Rules

- Start with a platform-neutral contract under `spec/components/`.
- Keep Web DOM/WASM internals out of Avalonia implementations.
- Use .NET-native models for batching, cancellation, virtualization, pooling,
  immutable snapshots, and UI-thread handoff.
- Every complex component needs empty, loading, error, permission, and
  cancellation states before preview.
- Every accepted platform difference must link to `spec/platform-overrides/`.

## Follow-Up Issue Split

Implementation must be split by component family. Do not mix these workstreams
into the first basic Avalonia control subset:

- `FsusDataTable`
- `FsusVirtualList`
- `FsusLogViewer`
- `FsusTerminalPanel`
- `FsusMarkdownViewer` and `FsusMarkdownEditor`
- `FsusFileManager`
- `FsusTree` and `FsusTreeTable`
- `FsusCodeBlock`

Each follow-up should include a contract file, performance/memory budget,
fixtures, accessibility plan, visual baselines, interaction traces, and
platform override review.
